# Dashboard patch workflow

- Keep the current release version unless the user explicitly requests a version increase. A patch must not bump `VERSION` or the displayed release number.
- Keep `/test-server/` as the public staging entry: the CVML Workspace sign-in (name and shared password). Link to this entry from the production header. Use `/test-server/preview.html` for the ongoing staging workspace (home, research tracker, GPU dashboard); preserve its entry check and separate administrator login. The production footer must not link to either test page unless the user asks to restore that button.
- All feature work happens on the test server first. Change the production page (`dist/index.html`, `dist/release/*`) only when the user asks to release to production. Files directly under `dist/` are shared by both pages: keep production behaviour unchanged when a staging feature needs them.
- The staging snapshot label (`v3.0 snapshot N` in `dist/test-server/index.html` and `preview.html`) is separate from `VERSION`. Raise it only for a staging change the user should be able to recognise on the page, and say so when reporting.
- Never write the workspace password or its document key into the repository, a commit message, or a test. Change the password only with `scripts/make_workspace_gate.mjs` (see `WORKSPACE.md`). Research records are stored sealed; keep commit messages on the `status` branch free of their contents.
- Before implementing a future dashboard patch, show the information notice `#maintenance-notice` in `dist/test-server/preview.html` by removing its `hidden` attribute. Publish this state and verify the notice on the live preview page before continuing the patch.
- When enabling the notice, update `#maintenance-start` and `#maintenance-end` in the test HTML with the current start and a reasonable completion estimate in Asia/Seoul. Keep their ISO `datetime` attributes and displayed KST times consistent. Do not reuse old dates; revise the estimate if work runs late. An estimated end time never replaces the checks required before hiding the notice.
- Use the test page to validate changes. Run the relevant existing checks and verify the requested behavior and responsive layout. Do not modify real experiment, parcel or research records for testing. Locally run `npm test`, `python3 -m unittest discover -s tests -p 'test_*.py'` and `GPU_TIMELINE_SKIP_FILMS=1 npm run test:browser` (the release films exist only in CI, which must run the suite without that switch; where Playwright is preinstalled rather than in `node_modules`, name its folder in `GPU_TIMELINE_NODE_MODULES`).
- If the session cannot open `https://shxyzn.github.io/`, verify what was deployed from the Pages artifact instead: download the `github-pages-<run>-<attempt>` artifact of the successful `Publish GPU Timeline` run for the pushed commit, unpack its `artifact.tar`, and run `node scripts/verify_deployed.mjs <site-dir> --notice visible|hidden --revision <sha>`. Say in the report that the live address itself was not opened.
- After the requested patch is deployed and all relevant checks and live verification pass, add `hidden` to `#maintenance-notice`, publish that change, and confirm the notice is hidden. Keep the notice visible while any failure or verification remains unresolved.
- Retain the notice markup and its stylesheet when hiding it so it can be reused. For the notice setup requested on 2026-11-02 only, leave it visible as requested. Every subsequent patch must follow the enable-before/hide-after cycle above.
